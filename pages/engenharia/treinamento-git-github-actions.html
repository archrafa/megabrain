Básico · Capítulo 1

Controle de versão e o modelo mental do Git

Na oficina

Antes do time chegar, a filha do Seu Arlindo tinha arquivos como estoque_final.xlsx, estoque_final_v2.xlsx e estoque_final_AGORA_VAI.xlsx. Ninguém sabia qual era o certo, nem quem tinha mudado o preço da pastilha de freio. É exatamente o problema que controle de versão resolve: quem mudou o quê, quando, por quê — e como voltar.

O que é o Git

O Git é um sistema de controle de versão distribuído: cada pessoa tem uma cópia completa do repositório, com todo o histórico. Não depende de servidor para commitar, ver log ou criar branch. O GitHub é só um lugar (muito conveniente) para hospedar uma cópia compartilhada.

Snapshots, não diferenças

A cada commit o Git grava uma foto completa do projeto (arquivos iguais aos do commit anterior são reaproveitados por referência, então não ocupa espaço duplicado). Cada commit é identificado por um hash SHA (ex.: a3f9c21), calculado a partir do conteúdo, do autor, da data e do commit pai. Mudar qualquer coisa muda o hash — é por isso que o histórico é à prova de adulteração.

As três áreas (o conceito mais importante do curso)

Por que existe a staging area? Porque você pode ter mexido em cinco arquivos mas querer commitar só dois — por exemplo, a correção do cálculo do orçamento separada do ajuste de layout. Commits pequenos e com um propósito único são mais fáceis de revisar e de desfazer.

Estados de um arquivo

EstadoSignificadoComo aparece no git status
UntrackedArquivo novo que o Git ainda não acompanhaUntracked files
ModifiedAcompanhado, alterado, ainda não adicionadoChanges not staged for commit
StagedAdicionado ao index, vai no próximo commitChanges to be committed
CommittedGravado no histórico, sem mudanças pendentesnothing to commit, working tree clean

Histórico e como desfazer coisas

Na oficina

Sexta-feira, 17h. Diego commitou "ajustes" três vezes seguidas. Uma delas quebrou o cálculo do orçamento. Seu Arlindo reclama que a OS 1032 saiu com valor negativo. Você precisa descobrir qual commit causou isso e desfazer sem apagar o trabalho dos outros.

Explorando o histórico

git log                                   # completo
git log --oneline --graph --decorate --all
git log -p src/TorqueOS.Application/Orcamento/CalculadoraOrcamento.cs   # histórico com diff de um arquivo
git log --author="Diego" --since="2 weeks ago"
git log -S "Desconto"                     # commits que adicionaram/removeram essa string ("pickaxe")
git log --grep="orcamento" -i             # busca na mensagem
git show a3f9c21                          # detalhes e diff de um commit
git blame CalculadoraOrcamento.cs         # quem alterou cada linha por último

Vendo diferenças

ComandoCompara
git diffWorking directory × staging (o que ainda não foi adicionado)
git diff --stagedStaging × último commit (o que vai entrar no commit)
git diff main..feature/xDuas branches
git diff HEAD~3 HEAD --statResumo das mudanças nos 3 últimos commits

Notação: HEAD~1 é o pai do commit atual, HEAD~2 o avô. HEAD^2 é o segundo pai de um merge commit.

Desfazendo: escolha a ferramenta pelo estágio

SituaçãoComandoDestrutivo?
Descartar alteração não adicionada em um arquivogit restore Arquivo.csSim, perde a edição local
Tirar da staging (manter a edição)git restore --staged Arquivo.csNão
Corrigir a mensagem/esquecer um arquivo no último commit (ainda não enviado)git commit --amendReescreve o último commit
Desfazer commits locais mantendo as mudançasgit reset --soft HEAD~1 ou --mixedReescreve histórico local
Jogar fora commits locais e mudançasgit reset --hard HEAD~1Sim (recuperável via reflog, cap. 14)
Desfazer um commit já compartilhadogit revert <hash>Não — cria um novo commit inverso

Os três modos do reset

ModoMove a branchStagingWorking directory
--softSimMantém (mudanças ficam staged)Mantém
--mixed (padrão)SimLimpa (mudanças ficam unstaged)Mantém

Regra de ouroCommit que já foi para o remoto e que outras pessoas podem ter baixado: use revert, não reset. Reescrever histórico compartilhado obriga todos a corrigirem seus clones e é a forma mais rápida de perder trabalho de colega.
Resolvendo o caso da OS 1032 
git log --oneline -- src/TorqueOS.Application/Orcamento/
# 9be41d0 ajustes
# 71c0a3e ajustes
# 4d2e8f9 feat(orcamento): aplica desconto por fidelidade
git show 9be41d0          # achou: sinal invertido no desconto

git push

Na retrospectiva, o time combina: nada de mensagem "ajustes". E Marina ativa uma regra de validação de mensagem (cap. 14, hooks).

Branches, merge e conflitos

Na oficina

Você está implementando o cadastro de veículos. Diego, o cálculo de orçamento. Se os dois commitarem direto na main, a main fica quebrada metade do tempo. Solução: cada um numa branch. Até que os dois mexem no mesmo método de OrdemServico.cs… e aparece o primeiro conflito.

Branch é só um ponteiro

git branch                         # lista branches locais (* = atual)
git branch -a                      # inclui remotas
git switch -c feature/cadastro-veiculo   # cria e muda (moderno)
git checkout -b feature/cadastro-veiculo # equivalente antigo
git switch main                    # volta
git branch -d feature/cadastro-veiculo   # apaga (só se já mergeada)
git branch -D feature/experimento        # força apagar
git branch -m nome-novo            # renomeia a branch atual
switch/restore × checkoutO checkout faz coisas demais (trocar de branch e restaurar arquivos). Desde o Git 2.23, switch cuida de branches e restore de arquivos. Você verá os dois em tutoriais; o laboratório aceita ambos.

Tipos de merge

git switch main
git merge feature/cadastro-veiculo            # fast-forward se possível
git merge --no-ff feature/cadastro-veiculo    # força merge commit (preserva o "bloco" da feature)
git merge --squash feature/cadastro-veiculo   # junta tudo em mudanças staged; você commita 1 vez

Conflitos: quando os dois mudaram a mesma linha

$ git merge feature/orcamento
Auto-merging src/TorqueOS.Domain/OrdemServico.cs
CONFLICT (content): Merge conflict in src/TorqueOS.Domain/OrdemServico.cs
Automatic merge failed; fix conflicts and then commit the result.

O Git marca o arquivo assim:

public decimal CalcularTotal()
{
<<<<<<< HEAD
    return Servicos.Sum(s => s.Valor) + Pecas.Sum(p => p.Preco * p.Quantidade);
=======
    return (Servicos.Sum(s => s.Valor) + Pecas.Sum(p => p.Preco)) - Desconto;
>>>>>>> feature/orcamento
}

Entre <<<<<<< e ======= está a sua versão (HEAD); entre ======= e >>>>>>>, a versão que está chegando. Resolver = editar o arquivo para o resultado correto (muitas vezes, uma combinação das duas), remover os marcadores e:

git add src/TorqueOS.Domain/OrdemServico.cs
git commit                  # conclui o merge (mensagem padrão já vem pronta)
# desistiu? 
git merge --abort
Resolução correta

Nenhuma das duas versões estava completa: a sua multiplicava pela quantidade, a do Diego aplicava desconto. O resultado certo combina as duas:

return Servicos.Sum(s => s.Valor) + Pecas.Sum(p => p.Preco * p.Quantidade) - Desconto;

Conflito não é erro — é o Git pedindo uma decisão de negócio que ele não pode tomar sozinho. Rode os testes depois de resolver.

Evitando conflitos grandesBranches curtas (1–3 dias), integração frequente com a branch base, commits pequenos, e combinar quem mexe em arquivos "quentes" (como o Program.cs ou o DbContext).
Pratique: crie duas branches que alteram o mesmo arquivo, gere um conflito e resolva.

GitHub: remoto, push, pull e Pull Requests

Na oficina

Até aqui o repositório estava só no seu notebook. Paula lembra: "Se o seu HD morrer, o TorqueOS morre junto." Hora de publicar no GitHub, na organização torque-cia, e de combinar que nada entra na main sem Pull Request.

Conectando ao remoto

# opção 1: criar o repo no site e conectar
git remote add origin git@github.com:torque-cia/torqueos.git
git remote -v
git push -u origin main          # -u: define upstream; depois basta "git push"

# opção 2: GitHub CLI cria e conecta de uma vez
gh repo create torque-cia/torqueos --private --source=. --push

# quem entra depois no time:
git clone git@github.com:torque-cia/torqueos.git

fetch × pull × push

ComandoO que faz
git fetchBaixa commits do remoto e atualiza origin/main etc. Não mexe nas suas branches. Seguro sempre.
git pullfetch + integração (merge, ou rebase se configurado) na branch atual.
git pushEnvia seus commits. É rejeitado se o remoto tem commits que você não tem (non-fast-forward).
git push --force-with-leaseForça, mas só se o remoto estiver como você viu no último fetch. Use sempre no lugar de --force puro, e só na sua própria branch.

origin/main é uma remote-tracking branch: a sua cópia local de "onde a main do GitHub estava no último fetch". git status mostra "ahead 2, behind 1" comparando com ela.

O fluxo de Pull Request

  1. Atualize a base: git switch main && git pull
  2. Crie a branch: git switch -c feature/42-notificacao-status
  3. Commits pequenos e com boas mensagens
  4. git push -u origin feature/42-notificacao-status
  5. Abra o PR: gh pr create --fill --base main (ou pelo botão no site)
  6. CI roda, alguém revisa, você ajusta com novos commits na mesma branch
  7. Merge pelo GitHub e exclusão da branch

As 3 opções de merge do botão do GitHub

OpçãoResultadoQuando
Create a merge commitPreserva todos os commits + merge commitQuer histórico completo da feature
Squash and mergeUm único commit na baseCommits da branch são "sujos"; quer histórico linear e limpo
Rebase and mergeReaplica cada commit na ponta da base, sem merge commitCommits já bem organizados e linearidade desejada

Boas práticas de code review

  • PR pequeno (idealmente < 400 linhas alteradas). PR de 3.000 linhas recebe "LGTM" sem leitura.
  • Descrição com contexto: o problema, a solução, como testar, prints se houver UI.
  • Vincule issues: Closes #42 no corpo fecha a issue ao mergear.
  • Use Draft PR para mostrar trabalho em andamento cedo.
  • Revisor: comente o código, não a pessoa; diferencie "bloqueante" de "sugestão (nit)".
Na oficina

Diego tenta dar push na main e recebe ! [rejected] main -> main (fetch first). Você já tinha empurrado a sua feature. Ele roda git pull, resolve o merge, e tenta de novo. Funciona — mas Marina aproveita para ativar a proteção de branch (cap. 9): a partir de agora ninguém faz push direto na main.

Pratique: configure um remoto simulado, faça push, simule um colega enviando commit e resolva com pull.

Git Flow, versionamento semântico e tags

Na oficina

O TorqueOS vai ter a primeira versão em produção: a 1.0.0, com clientes, veículos e OS. Seu Arlindo quer ver a versão rodando na homologação antes de ir para produção, e o time precisa continuar desenvolvendo a gestão de estoque (1.1) ao mesmo tempo. E se aparecer bug crítico em produção no meio disso? Vocês adotam o Git Flow.

As branches do Git Flow

BranchNasce deVolta paraPapel
main——Só código de produção. Cada merge = uma versão com tag.
developmain—Integração da próxima versão.
feature/*developdevelopUma funcionalidade.
release/*developmain e developEstabilização: só correções, versão, changelog. Vai para homologação.
hotfix/*mainmain e developCorreção urgente em produção.

Git Flow na mão (com comandos Git puros)

# preparação
git switch -c develop main && git push -u origin develop

# feature
git switch -c feature/cadastro-cliente develop
# ...commits...
git switch develop && git merge --no-ff feature/cadastro-cliente
git branch -d feature/cadastro-cliente

# release
git switch -c release/1.0.0 develop
# ajusta versão no .csproj, CHANGELOG, corrige bugs de homologação
git switch main    && git merge --no-ff release/1.0.0
git tag -a v1.0.0 -m "TorqueOS 1.0.0 - clientes, veículos e OS"
git switch develop && git merge --no-ff release/1.0.0
git branch -d release/1.0.0
git push origin main develop --tags

# hotfix
git switch -c hotfix/1.0.1 main
git commit -am "fix(os): impede OS com valor negativo"
git switch main    && git merge --no-ff hotfix/1.0.1 && git tag -a v1.0.1 -m "Hotfix 1.0.1"
git switch develop && git merge --no-ff hotfix/1.0.1
git branch -d hotfix/1.0.1

Com a extensão git-flow

A extensão automatiza as sequências acima (há a versão AVH, antiga, e a git-flow-next, mais recente; os comandos são equivalentes):

git flow init -d                       # -d aceita os nomes padrão
git flow feature start cadastro-cliente
git flow feature finish cadastro-cliente
git flow release start 1.0.0
git flow release finish 1.0.0          # merge em main e develop + tag
git flow hotfix start 1.0.1
git flow hotfix finish 1.0.1

O laboratório deste curso aceita esses comandos também.

Versionamento semântico (SemVer)

MAJOR.MINOR.PATCH — ex.: 2.4.1.

  • MAJOR: quebra de compatibilidade (mudou o contrato da API de OS).
  • MINOR: funcionalidade nova compatível (módulo de estoque).
  • PATCH: correção compatível (arredondamento do orçamento).
  • Pré-release: 1.1.0-rc.1; metadados: 1.1.0+build.87.

Com Conventional Commits, fix → patch, feat → minor, BREAKING CHANGE → major. Ferramentas como release-please, semantic-release ou GitVersion (popular em .NET) calculam isso automaticamente.

Tags

git tag                                    # lista
git tag v1.0.0                             # lightweight: só um ponteiro
git tag -a v1.0.0 -m "mensagem"            # annotated: tem autor, data, mensagem (use esta para releases)
git tag -a v0.9.0 9fceb02                  # tag num commit antigo
git push origin v1.0.0                     # tags NÃO sobem com git push comum
git push origin --tags
git tag -d v1.0.0 && git push origin :refs/tags/v1.0.0   # apagar local e remota
git switch --detach v1.0.0                 # inspecionar o código daquela versão

No GitHub, uma Release é uma página em cima de uma tag, com notas e binários anexos: gh release create v1.0.0 --generate-notes.

Rebase, stash, cherry-pick e squash

Na oficina

Rebase: reescrever a base da branch

O rebase pega os commits da sua branch e os reaplica em cima de outra base. O resultado é um histórico linear, como se você tivesse começado a feature agora.

git switch feature/estoque
git fetch origin
git rebase origin/develop
# conflito? resolva, depois:
git add .
git rebase --continue       # ou --skip, ou --abort para voltar ao estado anterior
git push --force-with-lease # os hashes mudaram, então o push precisa ser forçado
mergerebase
HistóricoPreserva exatamente o que aconteceu (com merge commits)Linear e limpo
HashesNão muda os existentesGera commits novos (hashes novos)
ConflitosResolve uma vezPode resolver commit a commit
Seguro em branch compartilhada?SimNão
Regra de ouro do rebaseNunca faça rebase de commits que outras pessoas já baseiam trabalho em cima (develop, main, branch compartilhada). Na sua branch pessoal de feature, é à vontade.
# pull com rebase: evita merges "Merge branch 'develop' of github..." poluindo o log
git pull --rebase
git config --global pull.rebase true   # tornar padrão

Rebase interativo: arrumar a casa antes do PR

git rebase -i HEAD~5
pick   a1b2c3d feat(estoque): cria entidade Peca
squash e4f5a6b wip
squash 7c8d9e0 agora vai
reword 1f2a3b4 teste
drop   5d6e7f8 console.log de debug

# pick = mantém | reword = muda mensagem | edit = para para alterar
# squash = junta ao anterior (edita msg) | fixup = junta e descarta msg | drop = remove

Truque profissional: faça commits de correção já marcados e deixe o Git organizar:

git commit --fixup a1b2c3d
git rebase -i --autosquash develop

Stash: guardar trabalho pela metade

git stash push -m "estoque: validação pela metade"   # limpa o working dir
git stash -u                    # inclui arquivos untracked
git stash list
git switch -c hotfix/bug-urgente main
# ...corrige, commita, volta...
git switch feature/estoque
git stash pop                   # reaplica e remove da pilha
git stash apply stash@{1}       # reaplica sem remover
git stash drop stash@{0}
Alternativa modernagit worktree (cap. 14) deixa você ter duas branches abertas em pastas diferentes ao mesmo tempo, sem precisar de stash.

Cherry-pick: trazer um commit específico

# o fix foi feito na develop, mas a release/1.1.0 já tinha saído e também precisa dele
git switch release/1.1.0
git cherry-pick 3e7a91c
git cherry-pick -x 3e7a91c      # -x anota "cherry picked from commit ..." na mensagem
git cherry-pick A..B            # um intervalo

Cherry-pick cria um commit novo com a mesma mudança (hash diferente). Use com moderação: se você se pega fazendo cherry-pick toda semana, o fluxo de branches provavelmente está complicado demais.

Squash

Três formas de chegar a "um commit por feature": git merge --squash, squash/fixup no rebase interativo, ou o botão Squash and merge do GitHub (o mais comum em times).

Anatomia

OIDC: deploy na AWS sem chave de acesso

Em vez de guardar AWS_ACCESS_KEY_ID como secret (chave de longa duração que vaza), o GitHub emite um token OIDC assinado para aquela execução. A AWS confia no provedor do GitHub e troca o token por credenciais temporárias de uma IAM Role — só se as condições (repo, branch, environment) baterem.

permissions:
  id-token: write     # necessário para pedir o token OIDC
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/torqueos-gha-deploy
      aws-region: us-east-1
  - run: aws sts get-caller-identity

A configuração do lado AWS (provedor OIDC e role) é feita com Terraform no próximo capítulo.

Segurança do pipeline (nível especialista)

  • Fixe actions de terceiros por SHA: uses: alguem/action@3f1e2d.... Tags podem ser movidas por quem controla a action (ataques reais de supply chain já exploraram isso).
  • permissions: mínimas no topo do workflow; aumente por job.
  • Cuidado com pull_request_target: roda com secrets no contexto da base — nunca faça checkout e execute código do PR nele.
  • Injeção de script: não interpole ${{ github.event.pull_request.title }} direto em run:; passe por env: e use "$TITULO".
  • Runners self-hosted em repositório público são perigosos: qualquer PR de fork pode executar código neles.

# .github/workflows/deploy.yml
on:
  workflow_call:
    inputs:
      environment: { type: string, required: true }
      image:       { type: string, required: false }

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}   # aqui entram aprovação e secrets do ambiente
    concurrency: { group: 'deploy-${{ inputs.environment }}', cancel-in-progress: false }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_DEPLOY }}
          aws-region: us-east-1
      - name: Resolve imagem
        id: img
        env:
          IMG: ${{ inputs.image }}
        run: |
          if [ -z "$IMG" ]; then
            REG=$(aws ecr describe-registry --query registryId --output text).dkr.ecr.us-east-1.amazonaws.com
            IMG="$REG/torqueos-api:${GITHUB_SHA::7}"   # mesma imagem homologada
          fi
          echo "image=$IMG" >> "$GITHUB_OUTPUT"
      - run: aws eks update-kubeconfig --name ${{ vars.EKS_CLUSTER }}
      - name: Helm upgrade
        run: |
          helm upgrade --install torqueos infra/k8s/chart \
            --namespace torqueos --create-namespace \
            -f infra/k8s/values-${{ inputs.environment }}.yaml \
            --set image=${{ steps.img.outputs.image }} \
            --wait --timeout 5m --atomic      # --atomic: rollback automático se falhar
      - name: Smoke test
        run: curl -fsS --retry 5 --retry-delay 10 "${{ vars.BASE_URL }}/health"

No Git Flow clássico o merge --no-ff da release na main cria um commit novo — então prefira: (a) re-taguear a imagem pelo commit da release (git rev-parse release/1.1.0) ou (b) registrar o digest homologado como output/artefato e reutilizá-lo. Git por dentro e ferramentas de especialista

Na oficina

Diego rodou git reset --hard na branch errada e "perdeu" dois dias de trabalho no módulo de notificação. Pânico. Você sorri: no Git, quase nada se perde de verdade. Para entender por quê, é preciso olhar dentro da pasta .git.

O modelo de objetos

ObjetoGuarda
blobConteúdo de um arquivo (sem nome).
treeUma pasta: nomes → blobs e subtrees.
commitPonteiro para uma tree raiz + pai(s) + autor + mensagem.
tag (anotada)Ponteiro para um objeto + autor + mensagem (+ assinatura).
git cat-file -t a3f9c21        # tipo do objeto
git cat-file -p a3f9c21        # conteúdo: tree, parent, author, mensagem
git cat-file -p 'HEAD^{tree}'  # a árvore do commit atual
git rev-parse HEAD             # hash completo
cat .git/HEAD                  # "ref: refs/heads/develop"
cat .git/refs/heads/develop    # um hash — a branch é só isso
git count-objects -vH          # tamanho do repositório

Objetos são endereçados por conteúdo (hash). Dois arquivos idênticos em pastas diferentes = um único blob. Periodicamente o Git compacta objetos em packfiles com compressão delta (git gc). O Git está migrando gradualmente de SHA-1 para SHA-256 como formato de hash; na prática diária nada muda para você.

Reflog: a rede de segurança

O reflog registra todo movimento do HEAD e das branches no seu clone local (commits, resets, checkouts, rebases). Por padrão, entradas ficam cerca de 90 dias.

$ git reflog
e4b1c7a HEAD@{0}: reset: moving to HEAD~3
9d2f0a1 HEAD@{1}: commit: feat(notificacao): template de e-mail de OS pronta
...
git reset --hard HEAD@{1}          # volta para antes do reset
git branch resgate 9d2f0a1         # ou cria uma branch apontando para o commit "perdido"

Também salva de rebase desastroso (ORIG_HEAD aponta para onde você estava antes) e de branch apagada sem merge. O que o reflog não salva: alterações que nunca foram commitadas nem adicionadas ao stash.

Bisect: busca binária pelo commit que quebrou

git bisect start
git bisect bad                 # o commit atual tem o bug
git bisect good v1.0.0         # essa versão funcionava
# o Git faz checkout no meio; você testa e responde good/bad... até achar o culpado
git bisect reset

# automatizado: o script retorna 0 = bom, 1 = ruim
git bisect run dotnet test --filter "FullyQualifiedName~CalculoOrcamento"

Em 1.000 commits, o bisect acha o culpado em ~10 passos. Funciona muito melhor quando todo commit compila (outro motivo para commits atômicos).

Worktree: várias branches abertas ao mesmo tempo

git worktree add ../torqueos-hotfix hotfix/1.1.1
# outra pasta, outra branch, mesmo repositório (.git compartilhado)
git worktree list
git worktree remove ../torqueos-hotfix

Ótimo para revisar um PR sem parar o seu trabalho, ou para rodar agentes de IA em paralelo, cada um na sua worktree.

Hooks: automação local

Scripts em .git/hooks/ executados em eventos: pre-commit, commit-msg, pre-push… Como .git/hooks não é versionado, use core.hooksPath ou ferramentas como Husky.Net, pre-commit ou lefthook.

  echo "Mensagem fora do padrão Conventional Commits"; exit 1

# .githooks/pre-commit — formatação

Commits assinados

Qualquer um pode configurar user.email com o seu e-mail. Assinatura prova a autoria. Hoje dá para assinar com a própria chave SSH:

Segredo vazou no histórico: o protocolo

git push --force --mirror

O que diferencia um especialista

  • Pensa no histórico como documentação: commits atômicos, mensagens com o porquê, PRs pequenos.
  • Sabe que quase tudo é recuperável (reflog) e por isso não entra em pânico — mas protege o que não é (segredos, dados).
  • Escolhe o fluxo de branches pelo modelo de entrega, e revisita a escolha com métricas (DORA).
  • Trata pipeline como produto: rápido, seguro (OIDC, SHA pinning, least privilege), reutilizável e observável.
