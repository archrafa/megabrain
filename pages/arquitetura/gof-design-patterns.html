1. O que é o Gang of Four (GoF)?

O Gang of Four (GoF) é o nome pelo qual ficaram conhecidos os quatro autores do livro 'Design Patterns: Elements of Reusable Object-Oriented Software', publicado em 1994: Erich Gamma, Richard Helm, Ralph Johnson e John Vlissides. A obra catalogou 23 padrões de projeto que solucionam problemas recorrentes no design de software orientado a objetos.

No contexto de Arquitetura de Soluções e Sistemas, os padrões GoF são ferramentas fundamentais que transcendem linguagens de programação: eles representam soluções arquiteturais testadas e aprovadas para desafios estruturais e comportamentais que surgem continuamente no design de sistemas corporativos, microsserviços, APIs, plataformas cloud e integrações complexas.

Por que o GoF é relevante para Arquitetos de Soluções?

Arquitetos utilizam padrões GoF para comunicar decisões de design de forma precisa, garantir manutenibilidade, escalabilidade e extensibilidade dos sistemas, e evitar soluções que criam dívida técnica. Conhecer os 23 padrões é o alfabeto do design de sistemas profissional.

CATEGORIA 1: PADRÕES CRIACIONAIS

Os padrões criacionais abstraem o processo de instanciação de objetos. Em arquitetura de sistemas, eles permitem que componentes de alto nível sejam independentes de como seus objetos colaboradores são criados, compostos e representados — aspecto crítico em sistemas distribuídos, multi-cloud e com inversão de controle (IoC).

2.1 Abstract Factory

Abstract Factory

🎯 Intenção

Fornece uma interface para criar famílias de objetos relacionados ou dependentes sem especificar suas classes concretas.

⚠️ Problema que resolve

Um sistema precisa ser independente de como seus produtos são criados, compostos e representados. Diferentes ambientes ou plataformas requerem diferentes implementações.

✅ Solução

Defina interfaces abstratas para cada tipo de produto. Crie fábricas concretas que implementam essas interfaces para cada família de produtos.

📌 Exemplo Arquitetural

Plataforma de pagamentos multi-gateway: Uma Abstract Factory para 'ConectorDePagamento' cria instâncias de ProcessadorPIX, ProcessadorCartao e ProcessadorBoleto. Há uma fábrica concreta para cada provedor (Cielo, Rede, PagSeguro), permitindo trocar todo o gateway sem alterar a lógica de negócio. Em cloud, uma fábrica abstrata de 'RecursosCloud' instancia StorageService, QueueService e DatabaseService, com implementações concretas para AWS, Azure e GCP.

2.2 Builder

Builder

🎯 Intenção

Separa a construção de um objeto complexo de sua representação, permitindo que o mesmo processo crie representações diferentes.

⚠️ Problema que resolve

Construção de objetos complexos com muitos parâmetros opcionais gera construtores telescópicos e código frágil. Diferentes variantes do mesmo objeto são necessárias.

✅ Solução

Separe o algoritmo de construção do objeto (Director) da construção passo a passo (Builder). O cliente usa o Director para orquestrar os passos.

📌 Exemplo Arquitetural

Construção de pipelines de dados: Um PipelineBuilder monta pipelines com etapas opcionais — fonte de dados, transformações, validações, destino — sem expor a complexidade de configuração. Também amplamente usado para construir objetos de Request em SDKs de APIs REST, queries SQL complexas em ORMs, e configuração de infraestrutura como código (Terraform builders, CloudFormation stacks).

2.3 Factory Method

Factory Method

🎯 Intenção

Define uma interface para criar um objeto, mas deixa as subclasses decidirem qual classe instanciar.

⚠️ Problema que resolve

Uma classe não pode antecipar a classe de objetos que deve criar, ou quer que subclasses especifiquem os objetos que criam.

✅ Solução

Declare um método abstrato de criação (factory method) na classe base. Subclasses implementam esse método e retornam instâncias de classes concretas compatíveis.

📌 Exemplo Arquitetural

Framework de conectores de integração: Uma classe abstrata ConectorMensageria define processarMensagem() com um factory method criarConsumer(). Subclasses KafkaConector, RabbitMQConector e SQSConector implementam criarConsumer() retornando o cliente correto para cada broker. Amplamente aplicado em frameworks como Spring (BeanFactory) e no padrão Repository do DDD.

2.4 Prototype

Prototype

🎯 Intenção

Especifica os tipos de objetos a criar usando uma instância-protótipo e cria novos objetos copiando esse protótipo.

⚠️ Problema que resolve

Criar objetos do zero é custoso ou complexo. O sistema precisa ser independente de como produtos são criados e representados.

✅ Solução

Implemente uma interface de clonagem nos objetos. O cliente clona o protótipo em vez de instanciar novas classes.

📌 Exemplo Arquitetural

Cache de configurações complexas: Em sistemas que carregam configurações pesadas de banco de dados (ex: regras de compliance de um banco), o Prototype permite clonar o objeto de configuração já populado em vez de recarregá-lo. Útil em engines de regras de negócio, criação de templates de contrato jurídico pré-populados, e replicação de configurações de ambiente em pipelines CI/CD.

2.5 Singleton

Singleton

🎯 Intenção

Garante que uma classe tenha apenas uma instância e fornece um ponto de acesso global a ela.

⚠️ Problema que resolve

Alguns recursos devem ter exatamente uma instância compartilhada por toda a aplicação (pools de conexão, registros de configuração, loggers).

✅ Solução

Controle a instanciação tornando o construtor privado e fornecendo um método estático que retorna sempre a mesma instância.

📌 Exemplo Arquitetural

Pool de conexões de banco de dados: Um DataSourceManager Singleton gerencia o pool de conexões JDBC ou de um cache Redis, garantindo que toda a aplicação compartilhe o mesmo pool sem criar conexões duplicadas. Utilizado em configuração de aplicações (application context do Spring), registro de métricas centralizadas e gerenciadores de cache (Redis client, Ehcache). Atenção: em arquiteturas distribuídas, o Singleton deve ser combinado com soluções de estado distribuído.

CATEGORIA 2: PADRÕES ESTRUTURAIS

Os padrões estruturais tratam de como classes e objetos são compostos para formar estruturas maiores. Em arquitetura de soluções, são especialmente relevantes em cenários de integração de sistemas legados, construção de APIs, orquestração de microsserviços e composição de interfaces complexas.

3.1 Adapter

Adapter

🎯 Intenção

Converte a interface de uma classe em outra interface que os clientes esperam. Permite que classes com interfaces incompatíveis trabalhem juntas.

⚠️ Problema que resolve

Sistemas existentes possuem interfaces incompatíveis com as interfaces esperadas pelos novos componentes. Integração sem modificar código legado.

✅ Solução

Crie uma classe Adapter que implementa a interface esperada pelo cliente e delega chamadas para o objeto adaptado (Adaptee) usando composição ou herança.

📌 Exemplo Arquitetural

Modernização de mainframe: Um AdaptadorCOBOL implementa a interface REST esperada pelos microsserviços modernos e internamente converte as chamadas para o formato de chamada COBOL/CICS do sistema legado. Padrão onipresente em integrações — adaptadores entre protocolos SOAP e REST, entre formatos EDIFACT e JSON, e em Anti-Corruption Layers do DDD que isolam o domínio moderno dos sistemas legados.

3.2 Bridge

Bridge

🎯 Intenção

Desacopla uma abstração de sua implementação para que as duas possam variar independentemente.

⚠️ Problema que resolve

Proliferação de subclasses quando abstração e implementação podem variar em múltiplas dimensões. Mudanças na implementação não devem afetar os clientes.

✅ Solução

Separe a hierarquia de abstração da hierarquia de implementação conectando-as através de uma referência (a 'ponte'), em vez de usar herança.

📌 Exemplo Arquitetural

Relatórios em múltiplos formatos e canais: A abstração Relatorio define gerarRelatorio(), e as implementações concretas RenderizadorPDF, RenderizadorExcel e RenderizadorHTML variam independentemente dos tipos de relatório (RelatorioFinanceiro, RelatorioAuditoria). Em mensageria, a abstração NotificacaoService pode operar com implementações de Canal independentes: EmailChannel, SMSChannel, WhatsAppChannel e PushChannel.

3.3 Composite

Composite

🎯 Intenção

Compõe objetos em estruturas de árvore para representar hierarquias todo-parte. Permite tratar objetos individuais e composições de objetos de maneira uniforme.

⚠️ Problema que resolve

Sistemas que processam hierarquias de dados precisam tratar objetos simples e compostos da mesma forma, sem lógica condicional.

✅ Solução

Crie uma interface comum para componentes folha e compostos. Componentes compostos mantêm uma coleção de filhos e delegam operações a eles recursivamente.

📌 Exemplo Arquitetural

Estrutura organizacional em RH/Jurídico: Um sistema de controle de acesso baseado em hierarquia (RBAC hierárquico) onde Departamento e Colaborador implementam a mesma interface Unidade, permitindo aplicar políticas de acesso a toda uma divisão ou a um colaborador individual de forma uniforme. Também aplicado em menus de sistemas ERP, árvores de categorias de produtos em e-commerce, e representação de portfólios de ativos financeiros com grupos e sub-grupos.

3.4 Decorator

Decorator

🎯 Intenção

Anexa responsabilidades adicionais a um objeto dinamicamente. Fornece uma alternativa flexível à herança para estender funcionalidades.

⚠️ Problema que resolve

Necessidade de adicionar comportamentos a objetos individualmente sem afetar outros objetos da mesma classe. Extensão por herança seria impraticável.

✅ Solução

Envolva o objeto original em um objeto Decorator que implementa a mesma interface e adiciona comportamento antes ou depois de delegar ao objeto original.

📌 Exemplo Arquitetural

Middleware de APIs e pipelines de requisição: Em um API Gateway, cada camada aplica um Decorator — autenticação JWT, logging, rate limiting, compressão GZIP, tracing distribuído — sem modificar o handler original. O Express.js e frameworks similares são implementações clássicas desse padrão. Em streaming de dados (Kafka Streams, Spark), transformações são decorators encadeados sobre um stream base.

3.5 Facade

Facade

🎯 Intenção

Fornece uma interface simplificada para um subsistema complexo.

⚠️ Problema que resolve

Clientes dependem de múltiplos componentes de um subsistema complexo, gerando acoplamento forte. A interface do subsistema é complexa demais para uso direto.

✅ Solução

Crie uma classe Facade que expõe uma interface simples e internamente orquestra o subsistema complexo, ocultando sua complexidade.

📌 Exemplo Arquitetural

API Gateway como Facade: Um serviço de 'ProcessamentoDeProposta' expõe um único endpoint POST /proposta que internamente orquestra chamadas ao serviço de análise de crédito, consulta ao bureau, avaliação de risco e registro no core bancário — tudo invisível ao cliente. O BFF (Backend for Frontend) é uma aplicação direta do Facade para mobile. Em sistemas de compliance como Bradesco Jurídico, uma FacadeDeAuditoria pode unificar múltiplos serviços de rastreabilidade.

3.6 Flyweight

Flyweight

🎯 Intenção

Usa compartilhamento para suportar eficientemente grande quantidade de objetos com granularidade fina.

⚠️ Problema que resolve

Grande número de objetos consome memória excessiva. Muitos objetos são idênticos em seu estado intrínseco e diferem apenas em estado extrínseco.

✅ Solução

Separe o estado intrínseco (compartilhável) do extrínseco (passado pelo cliente). Mantenha um pool (Flyweight Factory) de objetos compartilhados.

📌 Exemplo Arquitetural

Cache de metadados em sistemas de alto volume: Em um sistema de processamento de transações com milhões de operações por hora, os metadados de tipo de transação, moeda e produto financeiro são objetos Flyweight compartilhados em memória. Também aplicado em renderização de dashboards analíticos com milhares de elementos visuais, e em grids de dados de sistemas de trading onde cada linha compartilha metadados de coluna.

3.7 Proxy

Proxy

🎯 Intenção

Fornece um substituto ou espaço reservado para outro objeto controlar o acesso a ele.

⚠️ Problema que resolve

Necessidade de controlar acesso a um objeto, adicionar funcionalidades transversais (logging, cache, segurança) ou adiar criação de objetos custosos.

✅ Solução

Crie um objeto Proxy com a mesma interface do objeto real. O Proxy controla o acesso, adicionando comportamentos antes ou depois de delegar ao objeto real.

📌 Exemplo Arquitetural

Service Mesh e Sidecar Proxy: O padrão Istio/Envoy no Kubernetes é a implementação distribuída do Proxy — cada serviço tem um proxy sidecar que intercepta todo o tráfego, aplicando mTLS, circuit breaking, load balancing e observabilidade sem modificar o serviço. Em nível de aplicação, lazy loading de entidades JPA/Hibernate, cache de respostas de APIs externas e Virtual Proxy para conexões com sistemas de mainframe.

CATEGORIA 3: PADRÕES COMPORTAMENTAIS

Os padrões comportamentais são relacionados a algoritmos e à atribuição de responsabilidades entre objetos. Em arquitetura de sistemas modernos, são a base de workflows, event-driven architectures, pipelines de processamento e orquestração de microsserviços.

4.1 Chain of Responsibility

Chain of Responsibility

🎯 Intenção

Evita acoplar o remetente de uma requisição ao seu receptor, dando a mais de um objeto a chance de tratar a requisição. Encadeia os objetos receptores e passa a requisição ao longo da corrente.

⚠️ Problema que resolve

Mais de um objeto pode tratar uma requisição, e o handler não é conhecido a priori. A requisição deve ser passada pela cadeia sem o remetente conhecer o receptor.

✅ Solução

Construa uma corrente de handlers. Cada handler decide processar a requisição ou passá-la ao próximo da corrente.

📌 Exemplo Arquitetural

Pipeline de validação e aprovação em processos bancários: Uma solicitação de crédito passa por uma cadeia — ValidacaoCadastral, AnaliseDeRisco, ConsultaBureau, AprovacaoAutomatica, AprovacaoGerencial — cada handler processa o que é de sua competência e passa adiante ou interrompe. Em segurança da informação, uma cadeia de filtros (WAF -> AuthFilter -> AuthorizationFilter -> AuditFilter) é a implementação clássica no contexto de APIs.

4.2 Command

Command

🎯 Intenção

Encapsula uma requisição como um objeto, permitindo parametrizar clientes com diferentes requisições, enfileirar ou registrar requisições e suportar operações desfazíveis.

⚠️ Problema que resolve

Necessidade de parametrizar ações, suportar undo/redo, implementar filas de operações, logging de ações ou suporte a transações.

✅ Solução

Encapsule cada operação em um objeto Command com um método execute(). Opcionalmente, adicione undo(). Um Invoker armazena e dispara commands.

📌 Exemplo Arquitetural

Event Sourcing e CQRS: Em arquiteturas Event Sourcing, cada mudança de estado é um Command (CriarContaCommand, RealizarTransferenciaCommand) persistido como evento imutável. O CQRS separa Commands (escritas) de Queries (leituras). Em sistemas de auditoria (área crítica em compliance e jurídico bancário), todos os comandos ficam registrados permitindo reconstrução do estado em qualquer ponto no tempo.

4.3 Observer

Observer

🎯 Intenção

Define uma dependência um-para-muitos entre objetos para que quando um objeto muda de estado, todos os seus dependentes sejam notificados e atualizados automaticamente.

⚠️ Problema que resolve

Uma mudança em um objeto requer mudanças em outros, mas não se sabe quantos objetos precisam mudar. Acoplamento forte entre publicadores e assinantes.

✅ Solução

Defina uma interface Subject com métodos attach/detach/notify. Observers implementam uma interface update() e se registram no Subject.

📌 Exemplo Arquitetural

Event-Driven Architecture e mensageria: Kafka, RabbitMQ e AWS SNS/SQS são implementações distribuídas do Observer. Um evento 'TransacaoAprovada' publicado no tópico Kafka é consumido por múltiplos observadores: ServicoDeNotificacao, ServicoDeAntifraude, ServicoDeContabilidade e ServicoDeCompliance — completamente desacoplados. Em sistemas de monitoramento, alertas de SLO/SLA são implementados com o Observer.

4.4 Strategy

Strategy

🎯 Intenção

Define uma família de algoritmos, encapsula cada um e os torna intercambiáveis. Permite que o algoritmo varie independentemente dos clientes que o utilizam.

⚠️ Problema que resolve

Múltiplas variações de um algoritmo são necessárias e devem ser intercambiáveis em tempo de execução. Eliminação de condicionais extensos para seleção de comportamento.

✅ Solução

Defina uma interface Strategy. Implemente algoritmos concretos que a implementem. O contexto delega a execução à Strategy configurada.

📌 Exemplo Arquitetural

Motor de scoring e avaliação de risco em bancos: Um RiskAssessmentContext utiliza diferentes estratégias — EstrategiaScoreTradicional, EstrategiaMLScore, EstrategiaOpenFinance — de acordo com o perfil do cliente e produto, sem modificar o fluxo principal. Em sistemas de pagamento, estratégias de roteamento de transação entre redes (Visa, Mastercard, Elo) são intercambiadas em runtime baseadas em regras de custo e disponibilidade.

4.5 Template Method

Template Method

🎯 Intenção

Define o esqueleto de um algoritmo em uma operação, postergando alguns passos para subclasses. Permite que subclasses redefinam certos passos sem mudar a estrutura do algoritmo.

⚠️ Problema que resolve

Múltiplas implementações compartilham o mesmo esqueleto de algoritmo mas diferem em detalhes. Evitar duplicação do código estrutural.

✅ Solução

Defina na classe base um método template que chama métodos abstratos (hooks) em ordem fixa. Subclasses implementam apenas os hooks específicos.

📌 Exemplo Arquitetural

Frameworks de processamento batch: Um AbstractBatchJob define o template: inicializar() -> validarEntrada() -> processarRegistros() -> gerarRelatorio() -> finalizar(). Subclasses como ProcessamentoDeFolhaDePagamento e ConciliacaoFinanceira implementam apenas os passos específicos. Em integrações ETL, pipelines Spark e workflows de onboarding bancário, o Template Method garante que etapas obrigatórias (auditoria, log, notificação) sejam sempre executadas.

4.6 State

State

🎯 Intenção

Permite que um objeto altere seu comportamento quando seu estado interno muda. O objeto parecerá ter mudado sua classe.

⚠️ Problema que resolve

Comportamento de um objeto depende de seu estado e deve mudar em tempo de execução. Lógica condicional baseada em estado espalha-se pelo código.

✅ Solução

Encapsule cada estado em uma classe concreta que implementa a interface State. O contexto delega operações ao estado atual e permite transição entre estados.

📌 Exemplo Arquitetural

Máquina de estados de contratos e processos judiciais: Um Contrato possui estados (EmNegociacao, AssinadoPendente, Ativo, EmDisputa, Rescindido, Encerrado), cada um com comportamentos diferentes para assinar(), cancelar() e renovar(). Em processos judiciais de um banco, um ProcessoJudicial transita por estados (Notificado, Contestado, EmAudiencia, Sentenciado, Transitado) onde cada estado determina as ações permitidas.

4.7 Mediator

Mediator

🎯 Intenção

Define um objeto que encapsula como um conjunto de objetos interage. Promove fraco acoplamento evitando que os objetos se refiram explicitamente uns aos outros.

⚠️ Problema que resolve

Muitos objetos se comunicam de forma direta, gerando acoplamento forte e dificultando reutilização. Interações complexas são difíceis de entender e modificar.

✅ Solução

Crie um objeto Mediator que centraliza a comunicação entre objetos. Cada objeto conhece apenas o Mediator, não os outros objetos.

📌 Exemplo Arquitetural

Barramento de eventos corporativo (ESB/Event Bus): Um ESB como o MuleSoft ou Azure Service Bus atua como Mediator central — sistemas de CRM, ERP, Core Bancário e Compliance se comunicam apenas com o barramento, não diretamente entre si. Em microsserviços, o API Gateway com orquestração e o Saga Orchestrator são Mediators. Em sistemas de compliance, um MediadorDeAlerta coordena respostas entre sistemas de detecção, registro e notificação.

4.8 Iterator

Iterator

🎯 Intenção

Fornece uma forma de acessar sequencialmente os elementos de um objeto agregado sem expor sua representação subjacente.

⚠️ Problema que resolve

Necessidade de percorrer diferentes estruturas de dados de forma uniforme, sem expor detalhes de implementação interna das coleções.

✅ Solução

Defina uma interface Iterator com hasNext() e next(). A coleção retorna um Iterator adequado à sua estrutura interna.

📌 Exemplo Arquitetural

Paginação de resultados em APIs e consultas analíticas: Um CursorIterator para consultas a grandes volumes de dados (ex: extrato completo de transações) abstrai a paginação do banco, cursor de DynamoDB ou scroll de Elasticsearch. Em pipelines de dados, Iterators permitem processar streams de eventos Kafka, resultados de queries de data warehouse e arquivos CSV de grande volume sem carregar tudo em memória.

4.9 Outros Padrões Comportamentais

Os padrões abaixo completam a categoria comportamental e também têm aplicações relevantes em arquitetura:

  • Memento: Captura e externaliza o estado interno de um objeto sem violar encapsulamento. Aplicado em funcionalidades de undo/redo, snapshots de configuração de ambiente e versionamento de documentos e contratos.
  • Visitor: Representa uma operação a ser realizada sobre elementos de uma estrutura de objetos sem modificá-los. Amplamente usado em compiladores, análise de AST, e em sistemas de auditoria que precisam aplicar verificações variadas sobre uma estrutura de dados estável.
  • Interpreter: Define uma gramática para uma linguagem e um interpretador para lidar com essa gramática. Aplicado em engines de expressão de regras de negócio (BRMS), validadores de linguagens de consulta customizadas e configurações baseadas em DSL.

5.2 Princípios Subjacentes

Os 23 padrões GoF são sustentados por dois princípios fundamentais que todo arquiteto deve internalizar:

Princípio 1: Programe para interfaces, não para implementações

Dependências devem ser sobre abstrações (interfaces, classes abstratas), não sobre implementações concretas. Isso é o que torna os padrões criacionais e estruturais possíveis — e é a base da inversão de dependência (o 'D' do SOLID).

Princípio 2: Prefira composição de objetos à herança de classes

A herança cria acoplamento forte entre classes. A composição é mais flexível e é o mecanismo central de padrões como Decorator, Composite, Bridge e Strategy. Em arquiteturas de microsserviços, este princípio se traduz em serviços compostos em vez de hierarquias monolíticas.

5.3 Padrões mais Frequentes em Arquitetura Corporativa

Com base na aplicação prática em sistemas financeiros, cloud e integrações corporativas, os padrões de maior impacto são:

#PadrãoPor que é onipresente em arquitetura corporativa

1

Observer

É a espinha dorsal de qualquer EDA (Event-Driven Architecture). Kafka, SNS, EventBridge são implementações distribuídas deste padrão.

2

Facade

Todo API Gateway, BFF e orquestrador de serviços é um Facade. Fundamental para simplificação de interfaces em microsserviços.

3

Strategy

Permite que regras de negócio sejam trocadas sem modificar código. Essencial em sistemas financeiros com múltiplos algoritmos de precificação e scoring.

4

Adapter

Integração de sistemas legados é um dos maiores desafios corporativos. O Adapter é a ferramenta central de qualquer modernização ou Anti-Corruption Layer.

5

Decorator

Middleware chains em APIs, pipelines de processamento e aspectos transversais (logging, segurança) são todos Decorators.

6

Command

Event Sourcing e CQRS — arquiteturas cada vez mais adotadas em sistemas financeiros — são fundamentados no Command.

7

Template Method

Qualquer framework de processamento batch, ETL ou workflow de onboarding usa Template Method para garantir estrutura com flexibilidade.

5.4 GoF e Arquiteturas Modernas

Os padrões GoF, criados para OOP, se refletem diretamente em padrões arquiteturais modernos:

  • Microsserviços: Facade (API Gateway), Observer (Event Bus), Mediator (Service Mesh), Proxy (Sidecar)
  • Cloud-Native: Abstract Factory (multi-cloud resources), Singleton (managed connections), Decorator (middleware layers)
  • Event-Driven: Observer (pub/sub), Command (event sourcing), Chain of Responsibility (event processing pipelines)
  • Domain-Driven Design: Adapter (Anti-Corruption Layer), Facade (Application Services), Factory Method (Domain Factories)
  • Sistemas Legados/Modernização: Adapter (conversão de protocolos), Proxy (virtual services), Facade (simplificação de APIs legadas)

Conclusão do Arquiteto

Os 23 padrões GoF não são apenas código — são uma linguagem compartilhada. Quando um arquiteto diz 'vamos usar um Observer aqui', toda a equipe entende imediatamente a intenção, a estrutura e as implicações. Em sistemas corporativos de larga escala — como os encontrados em instituições financeiras, sistemas de compliance e plataformas de integração — o domínio desses padrões é o diferencial entre soluções que evoluem com o negócio e soluções que geram dívida técnica.
